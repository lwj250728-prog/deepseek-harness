# Agent Note：LLM 驱动的经验检索与经验网络

Status: proposed

[English](2026-08-18-llm-driven-experience-retrieval.md) | 中文

## 问题

认知流水线的检索完全确定。每条召回路径——热环的 `retrieveTopK`、orchestrator 的 `retrieve()`、`dsh-cognitive-inject` 的步骤预热——都用哈希词袋余弦加精确子串症状通道打分。LLM 路由只参与经验的*处理*（`extractSar`、`reviewOod`、`calibrate`、`reconstructTaxonomy`），从不参与经验的*检索*。对真实 bug 经验实测，确定性通道只在症状逐字出现在存储文本中时才命中短查询，且无法表达经验之间的同义、因果或冲突。

流水线的设计意图是以模型能力检索的经验网络（设计中的 `all-MiniLM-L6-v2` / `text-embedding-3-small` 检索轴），而非按哈希关键词匹配的平铺列表。当前实现把确定性下界当成了架构：[症状优先召回工作](../feature/2026-08-18-symptom-first-sar-extraction-and-recall.md)改善了地板，却没有迈向天花板。驱动这几轮的 bug 级细粒度处理是*下界展示*，不是设计目标。

## 提案

**混合检索架构：确定性粗召回 → LLM 精排 → LLM 综合。** 确定性通道保留为零成本候选生成器（它们已覆盖常见情形）；LLM 路由在已有模型调用的决策点成为排序与综合引擎。经验库在簇表之外新增显式关系网络。

### 第 1 层 — 粗召回（确定性，不变）

现有 `retrieveTopK` / `retrieve()` 余弦与症状通道保留为第一阶段，零 token 成本地产出候选集（当前 top-K，综合用途放宽到更大上限）。这保证步骤预热保持廉价：每个 `agent/pre-step` 仍只跑确定性召回，只有*是否注入*的决策才咨询模型。

### 第 2 层 — LLM 精排（新增，挂在既有 LLM 调用点上）

凡流水线已对同一输入发起模型调用之处，候选集随调用同行，由模型排序。具体而言：

- **热环**（`predict_outcome`）：OOD 复核已接收 top-3 行动并判定"已知变体 vs 陌生新物种"。扩展这一次调用，使其同时返回候选的相关性排序，于是 `predictKnown` 的样本按模型排序而非余弦排序。
- **orchestrator 注入决策**（`policy:inject`）：预测调用已框定任务；候选命中随调用传入，模型的校准概率成为注入决策——在同一调用内对候选排序，取代 `retrieve()` 的排序作为决胜。

精排*限定于已发生的调用*：步骤预热不引入新模型调用。契约是对所给候选 id 的 JSON 排序；路由缺失或调用失败时确定性回退到余弦序。

### 第 3 层 — LLM 综合（新输出形态）

检索返回的不再只是文本。在两个决策点（predict、orchestrator 注入），模型把排序后的候选综合成一条建议——"根据你上次修浮点下溢的经验与这次挂起症状，先二分定位，再把循环改成算术算法"——而非返回原始参考块。综合后的建议成为 `advice` / 注入块文本；候选 id 仍附着其上以供审计。

### 经验网络

簇表（`Cluster`）成为节点；新关系表记录节点之间的边。`reconstructTaxonomy` 的 LLM 调用扩展为在簇之外一并产出：

- **相似（similar-to）**：同一策略家族的经验或簇（冷环已计算此关系；现在持久化为显式边）。
- **因果 / 前置（causes / preceded-by）**：失败经验与其修复、其后结果相连——"我以前见过这个症状"的检索链。
- **冲突（conflicts-with）**：同一情境、不同行动、效用相左——"什么没起作用"的检索答案。

检索变成网络激活：粗召回播种节点，精排沿边扩散（相似预热兄弟节点，前置预热解决方案），再交给模型排序。这正是记忆链式语义：情境激活一个节点，边把模型即将考虑的邻居预先升温。

### 迁移路径

| 步骤 | 范围 | 交付 |
| --- | --- | --- |
| 1 | 扩展 OOD 复核与校准调用返回候选排序；确定性回退到余弦序 | 热环与 orchestrator 的 LLM 精排，无新增模型调用 |
| 2 | 扩展 `reconstructTaxonomy` 产出关系边；新关系表与 store 方法 | 经验网络的写侧 |
| 3 | 网络感知检索：粗召回播种节点，边预热邻居，精排消费升温集 | 经验网络的读侧 |
| 4 | predict 与注入的 LLM 综合：排序候选合并为一条建议块 | 天花板的输出形态 |

## 备选方案

**用 LLM 嵌入替换哈希向量。** 否决作为第一步：它需要新的嵌入 provider seam，每次经验写入与每次查询都要嵌入调用；而模型在决策点已被调用——在既有调用内精排今天就能交付语义排序，无需新依赖。

**把确定性检索当成天花板（现状）。** 否决：症状工作的实证展示了地板的极限——短查询只在症状逐字出现时命中，同义、因果、冲突在平铺余弦排序中不可表达。

**每一步前调用独立检索服务。** 否决：它在步骤预热处重新引入确定性粗召回本要避免的模型调用成本；只在决策点精排才能保持预热廉价。

**隐式存储网络（现场推导边）。** 否决：冷环本就要付出聚类一趟；持久化边让检索与分类法摘要跨进程确定、可复现，符合 store 既有的可复现契约。

## 验收标准

- 配置路由时，热环 `predict_outcome` 与 orchestrator `policy:inject` 通过模型对候选排序；未配置路由时与余弦序完全一致。
- 关系表存在，由 `reconstructTaxonomy` 填充，含三种边；检索在排序前跨边预热邻居节点。
- predict 与注入输出携带综合建议，候选 id 附着以供审计。
- 步骤预热不新增模型调用；步骤级注入保持确定性粗召回。
- 包测试、typecheck、lint 与文档门禁全绿；模型可见输出形态变化同步更新 keyless 快照。

## 风险

- **精排延迟**：既有调用上增加排序字段会加输出 token；以候选上限小、排序 schema 最小化来约束。
- **网络膨胀**：无边界的边会撑大存储；冷环的衰减加权采样已约束簇增长，扩展到边同理。
- **综合漂移**：模型组合的建议可能过度确定；注入块保留"参考而非当前事实"的框定，候选 id 仍可核查。
- **关系幻觉**：LLM 产出的边可能不成立；每条边在持久化前对端点向量做后端核验，镜像簇证据硬约束。
