# Agent Note: 数字生命智能体——认知基质上的一条连续主对话

Status: proposed

[English](2026-09-03-digital-life-agent.md) | 中文

## 问题

web profile 上的认知栈如今已逐块验证通过——embedding seam（SiliconFlow bge-m3，exp_11）、LLM 重构、回合末自动积累（auto-accumulate）、GUI 学习区气泡，以及情景状态链在链头存在时的 pre-step 注入（一个手工播种的 `sstate-1` 节点现以【情景状态参考】块出现在本会话上下文中）。每个机制单独都能工作，但合起来尚未兑现它们存在的目的：一条能自己保持思维线索的主对话——现在在做什么、类似情境以前怎么走过、以及一个持久身份——无论原始转录多长。

三个已核实的缺口挡住了这个结果。其一，情景状态链无法自行启动：链空时注入钩子短路，而唯一能创建首节点的 `situational_state_commit` 工具不在主对话的工具目录中（本会话暴露了认知管线工具如 `predict_outcome`，却不暴露情景工具）——首节点只能手工写入 `chain.json`。其二，上下文近似只是原始的 token 机制：`compaction-basic` 在 token 压力下压缩被挤出的 surface，但没有任何东西把被挤出的思维线索写回记忆基质（经验库、情景链），也没有任何东西在压缩后的第一步从基质恢复它——压缩后的连续性只靠静态摘要维持。其三，不存在"生命对话"这个概念：会话是按工作目录划分的 UUID，没有标记哪一个是持续对话，也没有定义的恢复路径把旧线索（当前状态、近期经验、活跃目标）交接给新会话。

运营者提出的功能要求：下一步发展是实现数字生命智能体，其可观察行为是一条通过认知管线与持续记忆插件近似无限上下文的主对话，连续性形态与人类思维一致——智能体始终知道自己正在做什么，记得类似事情以前怎么处理，且无需重新预热就能无限期地与之交谈。

## 方案

把数字生命智能体当作验证过的基质之上的一层薄产品层：指定一条持久的主对话，用四条相互配合的回路承载其连续性。每条回路都点名自己的所属 seam 与所需改动；不发明新的运行时——它们重连并补全 web profile 上已在运行的机制。

### L1——自持状态回路（所属包：@deepseek-ai/dsh-situational-state）

对话始终有一个已提交的当前状态：链头在每个 pre-step 注入（已验证），智能体在阶段切换时提交节点，过期的链头（超过 `staleUpdateGuideMs`，默认 1 小时）携带显式更新引导。三项修复关闭已核实的缺口：空链自举（指定主对话首次 pre-step 且无链头时，插件执行一次初始提交写入会话开场状态，而非短路）；工具暴露（通过已然暴露认知管线工具的同一注册路径，把 `situational_state_commit` 与 `situational_state_trace` 放进主代理工具目录）；以及回合末自检（回合完成后，当该回合的摘要/积累路径观察到阶段切换——新目标、环境变化、长任务边界——时条件性提交一个状态节点，让链自行推进，而不依赖模型记得调用工具）。

### L2——记忆回路与上下文近似（所属包：@deepseek-ai/dsh-cognitive-pipeline、@deepseek-ai/dsh-cognitive-inject、compaction seam）

完成的回合已自动积累进 SAR 库，pre-step 检索会重新注入相关经验（已验证）。缺失的另一半是记忆锚定压缩：在 `compaction-basic` 因 token 压力替换 surface 之前，把被挤出的线索写回基质——一次有界合成写入（一次情景状态提交记录"当时正在做什么"，外加至多一条经门控的经验概括被挤出的弧段）——并在压缩后的第一步，让检索从基质重新播种线索（链头加近期经验），而非只依赖静态摘要。写回是挂在既有 `ctx.compaction` seam 上的压缩监听器；写入发生在 surface 替换之前，因此崩溃不会造成"挤出但未持久化"。

### L3——身份回路（所属包：会话持久化、profile 配置）

一条持久的主对话身份：profile 级标记点名生命对话（其会话 id 与工作目录），任何 web 会话都能找到并恢复它。恢复 = 回放持久化的尾部、在首个 pre-step 注入情景链头、预热近期经验——把让运行中对话保持连续的同一套注入，应用到打开时刻。人格与系统提示的连续性沿用既有 persona 行。

### L4——表面回路（所属包：@deepseek-ai/dsh-ui-cognition、apps/web）

GUI 把主对话呈现为一条连续对话，并带相邻的生命流：当前已提交状态、情景轨迹条目（inject/commit）、学习区气泡事件，全部渲染在同一转录之上，让运营者看见维持线索的记忆活动。情景轨迹账本（`trace.jsonl`）与气泡事件已是现成数据；要做的是呈现，以及一条稳定回到指定对话的路径。

### 路线图

1. M0——本注记：商定路线、所属 seam 与 M1-M3 的验收标准。
2. M1——自持回路：L1 修复（自举、工具暴露、回合末自检）。可观察终态：从干净 home 出发，一条全新主对话无需任何手工播种即获得首个情景节点，并在真实阶段切换中推进链头，轨迹账本出现 commit/inject 成对记录。
3. M2——记忆锚定上下文近似：L2 写回与压缩后恢复。可观察终态：一段脚本化长对话跨越压缩边界，此后智能体能从基质回答"我们刚才在做什么/决定过什么"，以转录断言验证。
4. M3——身份与表面：L3 标记/恢复加 L4 呈现。可观察终态：关闭并重开浏览器（新会话 id）后恢复同一条生命对话，首个 pre-step 注入状态，GUI 显示带生命流的连续对话。

每个里程碑落地时自带各自的 implemented Agent Note 与验证；M0 只定路线。

## 备选方案

### 为何不扩大 token 窗口来替代上下文近似？

扩大窗口是推迟而非消除上限，成本线性增长，且不产生任何持久记忆：任何一次重置后运营者都得重新预热。基质已存在且已验证；要做的是把连续性接到它上面，而不是为原始上下文付费。否决。

### 为何不做只检索、从不积累的记忆？

纯检索存储文档（外部 RAG）能捕获事实，却捕获不了本对话的进行中状态，也捕获不了 auto-accumulate 路径记录的、由结果塑形的教训；它还没有反馈回路。管线的预测/回报回路恰恰是该备选方案会丢弃的积累。否决。

### 为何不把生命作为独立守护进程运行？

一个通过 IPC 与 GUI 对话的后台进程会拆散已验证的进程内插件 seam，增加生命周期机制（启停重启，包括已观察到的自反式宿主重启），还得复制上下文/注入管道。第一代形态是进程内的主对话；自主守护进程留待日后单独成注记。对 M1-M3 否决。

### 为何不做一条吞下全部四条回路的新巨型插件？

仓库规则是每个产品部件都是插件、每个插件只拥有一个 seam；一个同时拥有状态、记忆、身份与表面的协调者会重复并遮蔽已验证的属主。新层保持轻薄：属主包内的修复，外加一小层标记/呈现。否决。

### 为何不把所有会话一视同仁地当作"主对话"？

链与经验库本就跨会话共享；没有指定身份，链头会在最后一个发言者之间来回横跳，"生命"也会碎成片段而非一个连续整体。指定只是一个标记，不是限制——其他会话照常工作，只是它们不是生命对话。否决。

## 验收标准

### M0——本注记

路线商定：四条回路、各自的所属 seam、M1-M3 的顺序与树中实际存在的代码 seam 一一对应，且下列验收标准可评审。

### M1——自持回路

从干净的 `$DSH_HOME` 与一条全新主对话出发：链自动获得首节点（无需手工编辑 `chain.json`、无需手工调用工具），对话在真实阶段切换中推进链头，`situational_state_trace` 能列出该会话的 commit/inject 条目。commit 与 trace 工具可从主对话调用。

### M2——记忆锚定上下文近似

一段长到跨越压缩边界的脚本化对话：边界之后，智能体能从基质恢复线索——它能说出自己在做什么、决定过什么——以转录断言验证；经验库显示有界写回（一个情景节点、至多一条经门控的经验），而非洪泛。

### M3——身份与表面

浏览器关闭/重开并携带新会话 id 后，恢复同一条指定对话：首个 pre-step 注入情景链头，近期经验可检索，GUI 渲染出可见生命流的连续对话。

## 风险

压缩写回必须在 surface 替换前持久化，否则"挤出与落盘之间崩溃"会在回放时丢失线索；因此监听器先写后压，且合成写入幂等（重启重试不得重复建节点）。自反式中断（智能体回合中途重启自身宿主）本就会打断引用结算与 pre-step 工作；自举与回合末提交必须容忍重启、绝不双提交。暴露 `predict_outcome` 却不暴露 `situational_state_commit` 的工具目录 seam 尚未在代码中定位——M1 从找到它开始，沿已被暴露的认知工具所用注册路径推进；若该 seam 很深，修复或需单独成注记。M3 的 GUI 一半触及 `apps/web` 与客户端包，其产物需要重建加刷新验证（shell 无 HMR）；M3 必须为此预留步骤。自动积累有五门过滤，但压缩时刻的合成写入不得成为第二条未经审查的入流——它们复用同一套门控，且每次压缩至多一条。
